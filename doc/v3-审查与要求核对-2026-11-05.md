# v3 审查与课程要求核对

审查日期：2026-11-05。

审查对象：`https://github.com/whynotcooper/backup.git`，提交 `47089f98c0826b515c683fb8b8605ca20c0c63c9`；对照原版 `6d5a5bfe7c1e2f6878a785c94e3eb268b5eeb924` 及用户提供的《v3-修改说明.md》。

结论：**新增功能有价值，但当前版本不宜直接按“全部补齐、全部验证”合入正式演示版本。** 属主筛选已落地；特殊文件恢复和网络流程存在已复现的问题。此次只审查，在临时副本运行测试和复现程序，未修改或合并两个仓库的产品代码。

## 1. 先统一评分依据

目前材料中存在两个评分口径：

| 项目 | 最初提供的评分截图 | 仓库《实验报告模板.md》 |
| --- | --- | --- |
| 自定义筛选 | 路径、类型、名字、时间、尺寸，五类，各 5 分 | 上述五类加用户，六类，各 3 分 |
| 特殊文件举例 | 管道、软链接、硬链接等 | 管道、链接、设备等 |
| 扩展项目 | 根据情况自行选择 | 可任意选择扩展要求 |

因此，属主筛选是按模板补充的能力，不能仅凭最初截图认定原版漏掉了必选项，也不能混用两套分值计算扣分。管道、设备支持有助于争取文件类型扩展分，但必须实际恢复成功。

网络是扩展选做项，原版删除网络是用户明确决定的范围调整，不是遗忘实现。v3 重新加入网络属于范围扩大，需要另外验证演示条件。

更正此前粗估中的算术：若把最初截图所有明列分值全部相加，得到的是 **180 分而非 170 分**；这不是老师最终成绩的计算公式，扩展选择、封顶和验收规则仍应以老师当前口径为准。不再依据这些合计推算精确完成率或保证分数。

## 3. 必须先修的问题

### R1 · P1：FIFO 还原会卡住

位置：[ArchiveService.java:311](https://github.com/whynotcooper/backup/blob/47089f98c0826b515c683fb8b8605ca20c0c63c9/src/main/java/com/backup/io/ArchiveService.java#L311)。

复现：在临时目录用 `mkfifo` 建管道，正常扫描、ZIP 打包，再调用 `restoreDetailed`。FIFO 本身创建成功，但还原超过 5 秒不返回。线程栈确认停在：

```text
UnixNativeDispatcher.open0
UnixFileAttributeViews$Posix.setMode
UnixFileAttributeViews$Posix.setPermissions
ArchiveService.applyMetadata / lambda:313
ArchiveService.finish
```

原因：新支持的 FIFO 进入了原本处理常规文件的权限回填流程；当前 JDK 的该调用打开 FIFO 并等待写入端。相同元数据流程也用于 GZIP 还原。

影响：按说明进行管道演示会停在还原中，备份/还原任务互斥也无法释放。当前不能宣称“FIFO ZIP/GZIP 往返已通过”。

修复方向：特殊文件使用不会打开其数据流的属性操作；不能仅给外层 Future 加超时后继续假装成功。增加带明确超时的真实管道往返测试，保证还原完成、类型正确、失败可报告。

### R2 · P1：父链被淘汰后，服务端仍接受不可完整还原的增量

位置：[NetworkBackupServer.java:214](https://github.com/whynotcooper/backup/blob/47089f98c0826b515c683fb8b8605ca20c0c63c9/src/main/java/com/backup/network/NetworkBackupServer.java#L214)。

已复现的合法操作交错：

1. 提交全量组 A，保留 1 组。
2. 一个客户端基于 A 准备并上传增量，暂未 commit。
3. 另一个客户端提交新全量组 B，保留策略删除 A。
4. 第一个客户端提交旧增量，服务端仍返回成功并在列表中展示。

复现输出：`PARENT_PRUNED=true`、`ORPHAN_ACCEPTED=true`，恢复该增量后未变文件缺失。服务端没有在发布时验证父链仍存在，且依赖验证、提交、淘汰未作为同一任务的协调操作。

修复方向：在服务端校验完整父链及任务/组/序号关系，并把校验、发布、淘汰放到同一账号/任务的受控操作中；父链已失效时拒绝提交，要求客户端重建全量。不能仅靠 UI 的单进程门控保证多个客户端安全。

### R3 · P2：独立客户端/局域网连接路径没有打通

位置：[BackupFrame.java:496](https://github.com/whynotcooper/backup/blob/47089f98c0826b515c683fb8b8605ca20c0c63c9/src/main/java/com/backup/ui/BackupFrame.java#L496)、[NetworkBackupClient.java:197](https://github.com/whynotcooper/backup/blob/47089f98c0826b515c683fb8b8605ca20c0c63c9/src/main/java/com/backup/network/NetworkBackupClient.java#L197)。

有两个独立障碍：

- UI 只有在同一程序实例启动过服务端时才传入该服务端的信任库；独立客户端没有证书导入/选择入口，会回退到系统默认信任。已复现 `SSLHandshakeException: PKIX path building failed`。
- 即使代码手动传入信任库，生成证书的 SAN 也仅含 localhost 和 127.0.0.1；客户端代码没有实际关闭主机名检查。用已信任的证书连接 `[::1]` 仍报 SAN 不匹配；真实局域网 IP 同样不在现有 SAN 中。

因此现有测试可证明同机 localhost 流程可用，不能证明两台机器从 GUI 连接可用。

修复方向：为客户端提供可信证书导入，使用匹配实际服务地址的证书身份并保留校验。分发的是公钥证书/客户端信任材料，不应以分发含服务器私钥的整个密钥库作为默认解决办法。

### R4 · P2：GUI 中开启加密后，后续网络备份始终全量

位置：[BackupFrame.java:565](https://github.com/whynotcooper/backup/blob/47089f98c0826b515c683fb8b8605ca20c0c63c9/src/main/java/com/backup/ui/BackupFrame.java#L565)、[NetworkBackupService.java:69](https://github.com/whynotcooper/backup/blob/47089f98c0826b515c683fb8b8605ca20c0c63c9/src/main/java/com/backup/network/NetworkBackupService.java#L69)。

每次点击按钮都 `new NetworkBackupService()`，使其密码记忆 Map 每次为空；密码一致性检查失败后降为全量。集成测试重复使用一个 service，因此没有覆盖真实 UI 生命周期。

按 UI 创建方式实测：第一份 `full=true`，第二份仍 `full=true, sequence=1`。改用同一个 service 后第二次为 `full=false, sequence=2`。

修复方向：按连接/账号/任务持有正确的会话状态，切换服务器、用户或密码后明确失效；用与 UI 相同生命周期的流程验证加密增量。

### R5 · P2：保留历史时，第 11 份以后不再继续增量

位置：[NetworkBackupService.java:49](https://github.com/whynotcooper/backup/blob/47089f98c0826b515c683fb8b8605ca20c0c63c9/src/main/java/com/backup/network/NetworkBackupService.java#L49)。

`latest` 先按 sequence 最大、再按时间选择，导致旧组的 sequence 10 永远压过新组的 sequence 1。默认保留值 0 下实测：第 1～10 次序号正常，第 11、12、13 次都是全量序号 1。

已有网络保留测试只用 `keepGroups=1`，旧组被删后恰好掩盖此问题。修复应先确定最新有效快照/活动组，再判断其链长，并覆盖保留值 0、1、大于 1 和手动创建新全量等场景。

### R6 · P2：特殊文件创建失败可以被静默当成成功

位置：[ArchiveService.java:187](https://github.com/whynotcooper/backup/blob/47089f98c0826b515c683fb8b8605ca20c0c63c9/src/main/java/com/backup/io/ArchiveService.java#L187)。

若目标处已有普通文件，`mkfifo/mknod` 返回失败时，因为该路径仍存在，代码不添加“未重建”警告。用临时假 mkfifo（仅返回非零退出码）安全复现：`regular=true warnings=[]`，清单声明的管道实际上仍是旧普通文件，甚至会给旧文件回填管道的元数据。

修复方向：根据操作成功和最终文件类型判断结果，不以“路径存在”代替成功；对失败保留原目标、报告原因，且不要给错误类型的对象回填快照属性。

## 4. 其他需要补测或修正文档的内容

- **设备基线身份检查不足：**`ArchiveService.java:270` 只比类型，不比主/次设备号。只读复现：把实际 `/dev/null` 声明成字符设备 `99:99`，`baselineMatches` 仍为 true，实际设备号是 `3:2`。同类不同设备不能视为正确基线。
- **快照选择使用列表下标：**`BackupFrame.java:625` 在执行操作前重新查询列表，却沿用旧下标。另一客户端新增快照导致排序变化后，可能还原或删除与界面显示不同的快照/组。应把稳定 snapshotId/archiveName 绑定到下拉项并按 ID 校验，避免按新列表同下标取对象。此项为代码路径确认，未进行破坏性 UI 删除复现。
- **PPT 说明仍自相矛盾：**顶部加了 v3 更新，但后文仍写不支持网络、64 项、三标签页，源素材截图也属于 v2。应真正更新逐页内容、讲稿、测试表及截图，而不是只加一段覆盖声明。
- **演示时限：**老师给的是 PPT 介绍 2 分钟、软件操作 8 分钟；v3 说明的“3 分钟演示要点”可当局部功能示例，不能当作新的课堂要求。
- **平台验证边界：**管道/设备要在实际演示的 POSIX 环境验证，设备创建需要权限。Windows 跳过测试不能证明这些功能在 macOS/Linux 当前 v3 已通过；本次真实 FIFO 复现恰好发现卡死。

## 5. 按课程项目逐项结论

| 项目 | 本次核对结论 |
| --- | --- |
| 基础备份/还原 | 原有常规文件路径通过，新增特殊文件还原有阻断问题，不能整体无条件打勾 |
| 文件类型扩展 | 链接原有能力仍有测试；FIFO 可扫描和打包但恢复卡住；设备与 socket 不能以“枚举存在”代表完整支持 |
| 元数据 | 原有常规文件/目录与链接限制仍在；新增特殊文件须单独设计和验证属性回填 |
| 自定义备份 | 原五类在；属主作为第六类已实现，是否对应额外分值需统一老师口径 |
| 打包/压缩/密码加密 | 有实际实现和正常路径测试，仍使用 JDK 标准算法，不应称自研压缩或密码算法 |
| 图形界面 | 有对应入口；网络 UI 的连接与会话生命周期尚有缺陷 |
| 定时+淘汰/实时备份 | 原本地能力有测试，不是 v3 才补齐；新增服务端依赖淘汰有交错问题 |
| 网络扩展 | 新增认证、TLS、清单、列表下载和增量编排，不是空壳；但客户端可达性、增量和依赖正确性未全部过关 |
| 测试和文档 | 当前可复现 80 项通过；缺六项特殊文件测试，存在测错位置的断言和文档冲突 |

## 6. 建议处理顺序

1. 先补齐并提交缺失的特殊文件测试，修好 FIFO 阻塞和失败误报，再谈文件类型扩展验收。
2. 属主筛选可作为独立补丁吸收。注意提交 `780d006` 同时包含特殊文件代码，不能把整个提交直接当成“只有属主筛选”。
3. 若决定保留网络，先修客户端证书入口、GUI 会话、活动链选择和父链提交保护，再做两程序/两机器演示及完整回归。
4. 若仍维持不启服务器的选择，可保留稳定本地版本，把网络留在独立开发线；不必因选做项未启用而推倒本地方案。
5. 最后同步修改说明、测试计数、PPT 正文和截图；人员分工、真实进度与最终评分仍由项目组/老师确认。

本次所有复现仅使用临时目录和短时测试服务，测试进程已结束；原项目主线和对方仓库未作提交或推送。
